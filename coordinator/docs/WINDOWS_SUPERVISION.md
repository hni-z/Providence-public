# Existing-enrollment Windows supervision

This legacy launcher is separate from the current [hosted installation](FIRST_RUN.md) and its background helper. It is also separate from pairing/bootstrap and the shared client lifecycle. It consumes an already prepared runtime, existing private enrollment, and explicit native Node/Codex paths. It never installs dependencies, authenticates, edits enrollment or permission preferences, or replays work.

The shared-client exit contract is exit `0` for deliberate shutdown, `78` for action-required terminal failures, and `75` for an explicitly classified unexpected process defect. Transient connection/runtime recovery stays inside the shared client. The supervisor retries only `75`, at most three times with delays of 2, 4, and 8 seconds. Every other exit and exhausted retries write a persistent `stopped.json` gate. Subsequent logons stop until an operator reviews the cause and explicitly uses `-ResumeAfterReview`.

`supervise-windows.ps1` holds a named Windows mutex keyed by the current user's SID and a digest of the validated coordinator URL plus device ID. Hardlinks, copied configurations, different names, and path aliases for the same enrollment share ownership. The token is neither part of the key nor exposed. Before launching, it parses existing process command lines with the Windows argument parser, identifies `device.ts` plus its config argument, and compares validated enrollment identities without assuming the executable is named `node.exe`. Different enrollments with the same config basename do not conflict. Ambiguous/unreadable companion configs stop preflight; no uncertain process is killed. This detects existing unmanaged companions, but cannot prevent an unrelated launcher that ignores the mutex from starting later.

The child starts suspended, enters a Windows job with kill-on-close, and only then runs. If the supervisor exits, its owned child tree stops. No privileged service or scheduled task is created. This is user-session availability, not pre-login availability; the per-user global mutex also covers concurrent Windows sessions for that user.

`%LOCALAPPDATA%\Providence\supervisors\<identity digest>` stores ownership status, the terminal gate, and separate stdout/stderr logs under the existing private Providence directory. `status.json` reports process ownership only. Shared client readiness must come from an actual matching server `ready_ack` before Watch dispatch; neither a PID nor socket-open log proves readiness or a successful task. The standalone launcher cannot prove readiness by itself. The token never appears in arguments or launcher status.

Invalid/missing enrollment identity writes a sanitized preflight gate keyed to the launch config path, since no valid enrollment identity exists. Missing runtime/executable and later launcher failures write the enrollment's terminal gate. These gates survive logon and need `-ResumeAfterReview`; a corrected file alone does not silently resume execution. Ownership conflicts do not write terminal gates because another healthy owner may be running. An ambiguous unmanaged process aborts each invocation before starting any child. Failures before the script can load its helper or access its private state directory cannot be persisted by the script; Windows logon invokes it once, with no installer retry policy.

After verifying the configured runtime and confirming no unresolved work, run the supervisor hidden with `powershell.exe -NoProfile -NonInteractive -WindowStyle Hidden -ExecutionPolicy Bypass -File <supervise-windows.ps1>` and explicit `-CoordinatorDirectory`, `-ConfigPath`, `-NodeExecutable`, and `-CodexExecutable` paths. The installer accepts the same four parameters and creates one current-user Startup shortcut. It does not start the companion, overwrite an existing shortcut, or add automatic terminal-gate reset. `-WhatIf` previews registration. Remove that exact shortcut to disable future logon starts; stop the owned supervisor only after the coordinator confirms idle. The job then stops its own child tree.

The `test-windows-supervisor.ps1` integration harness uses inert temporary Node fixtures with synthetic registration identities, no credentials or network. It verifies exit classification/retry bounds, persistent stop gates including a copied enrollment, exclusive ownership across a differently named hardlink, renamed unmanaged executable detection, no false conflict for different enrollments with the same basename, runtime and malformed-config preflight failures without config-content leakage, and descendant cleanup. Production acceptance is separate: a coordinated idle transition followed by one fresh normal Providence UI task producing a visible Windows browser result with actual readback. Historical shell output and online flags do not satisfy that acceptance. Full access must match the saved `workerAccess` configuration and actual provider-offered scopes; this launcher has no grant behavior.
